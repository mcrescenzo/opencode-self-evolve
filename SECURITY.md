# Security Policy

## Reporting

Report security issues privately through GitHub Security Advisories for `mcrescenzo/opencode-self-evolve`. Do not open a public issue for an undisclosed vulnerability. Never include live secrets; use synthetic values that preserve the relevant token shape.

Relevant reports include privacy-boundary bypasses, synthesizer/critic isolation failures, host-source misclassification, automation-epoch or no-backfill failures, unsafe path handling, stale-hash or symlink bypasses, unauthorized application, audit/rollback defects, synthetic transcript injection, and unexpected external mutation.

## Dependency Advisories

Dependabot checks the Bun lockfile weekly. `npm run audit:dependencies` runs Bun's JSON audit and independently verifies recognized advisory metadata, the exact installed version and dependency path in `bun.lock`, and the advisory-specific applicability classification. It fails closed for malformed output, unknown or changed advisories, changed paths, and every unresolved finding.

`npm run audit:dependencies` is a mandatory publication gate. `npm run pack:check` and the release-artifact script both run it before any pack or publication-capable operation, and a failing audit fails the pack/release closed.

Only the repository owner may accept temporary dependency risk. An acceptance must be a bounded JSON record under `security/audit-exceptions/` with the advisory URL, exact package/version/path and applicability, narrow scope, accountable owner, review date, and expiry. Agents and automation must not create or renew these records. The `reviewDate` is the calendar date the owner actually reviewed the live advisory, dependency path, and applicability, and it must be on or before the evaluation date (today); a future `reviewDate` is rejected because it would defeat mandatory periodic review. `expiresOn` must be on or after `reviewDate`, and an expired record fails the gate. Expired, future-dated, or mismatched records fail the gate; dependency overrides and unsupported peer resolutions are not exceptions.

## Privacy Classes

- Complete transcripts and raw message bodies are never stored.
- Deterministic receipts and typed observations are stored without raw text.
- Sanitized evidence excerpts require the retained `sanitizedExcerpts` permission, are length-bounded, and have a short lifetime. Fresh v0.4 starts with the required permission bundle enabled; any permission may be revoked.
- Skill hashes are durable. Proposal bodies are bounded typed chunks tied to one proposal ID and proposed-content hash. Readers reject cross-proposal, mixed, duplicate, partial, non-canonical, or hash-mismatched sets. Bodies exist only while required by an active proposal and are replaced by hashes when it closes.
- Cross-project aggregation requires both sanitized excerpts and the retained cross-project permission. Global contributions and support use exact normalized schemas and contain no project/worktree/source-domain/capsule/observation/session/local-incident identity or derived hash; opaque contribution IDs are random.
- Observations and observation-like evidence default to 30-day retention; proposals, decisions, audits, rollback/intervention/circuit records, and snapshots to 90 days; and decision/control/operation bridge envelopes to a fixed 24 hours. The operational TUI host-version report expires within 60 seconds, is revoked on clean TUI disposal, and is omitted from exports. Native export artifacts have a separate short expiry and are deleted by project or all-state purge. Aggregate claims receive a 30-day default explicit expiry when created. Active critic-pending/pending/approved/applied chains, required proposal content, and snapshots remain until terminal. Terminal transitions and proposal purge compact content immediately under the transaction lock; boot/read recovery finishes interrupted compaction before records are exposed or exported.

Redaction is defensive, not a secrecy guarantee. Users should not process material that must never reach their configured model provider.

## Applier Boundary

The applier is the only code path authorized to write skill files. Existing edits require a fresh host-global source/catalog/path/content binding; new targets require one explicit canonical creation root and the exact `must-not-exist` sentinel. Project, remote, embedded, cache, ambiguous, malformed, symlinked, or drifted targets fail closed. Existing writes use a complete same-directory temporary file and atomic rename. New files are fully written and validated before an atomic create-exclusive hard link publishes the complete inode; the temp name is then unlinked. Readers therefore see absence or complete content, never an empty reservation. Filesystems that do not support this hard-link primitive fail closed without a rename fallback. Exact readback hashing, append-only audit, and rollback guarded by `currentHash == appliedHash` remain mandatory. Source/config disagreement, scope ambiguity, stale hashes, collisions, privacy or injection flags, lease conflicts, missing creation authority, secret canaries, growth limits, audit failure, and rollback uncertainty all fail closed.

Every Apply and Undo approval is per change. TUI and headless approval bind the recommendation ID, current target hash, proposed-content hash, exact decision version, and a server-issued one-use nonce. Missing, mismatched, stale, or replayed tuples cannot authorize mutation. Automatic recommendations On never creates an operator edge, and ordinary Off is not action authority or an action suppressor. Privacy revocation blocks Apply but preserves Reject and exact integrity-proven Undo; restored privacy may restore Apply while automation remains Off. Emergency Stop and breaker state block new Apply but cannot strand exact risk-reducing Undo.

Every automatic provider call requires Automatic recommendations On, all required permissions, a fresh exact automation generation, terminal/breaker authority, budgets, target proof, a process-aware lease, and a prior strict content-free synthesis-attempt admission. Off or generation mismatch aborts at every material boundary; late output cannot settle into new evidence, support, recommendation, or result authority. Recovery is idempotent, supersedes only defined unfinished old-generation states, preserves published recommendations, and never backfills Off-window activity after re-enable.

## Cross-Process TUI Boundary

The TUI may write only create-exclusive authenticated envelopes in the separate decision, control, and operation request namespaces under `<stateRoot>/self-evolve/bridge/<projectFingerprint>/`, plus one replaceable short-lived `tui-host-health.json` runtime report. It reads strict server-authored projections and bounded inspection summaries but is read-only for global/repository settings and project records. Projections bind a SHA-256 identity of the selected canonical root; the TUI validates it before reads or submissions, so an explicit/projection mismatch fails closed. Control and operation requests bind the project, actor, timestamp, request ID, exact allowlisted action payload, target-derived generation/domain versions, and a server-issued one-use nonce. The server consumes every request namespace under one mailbox lease, freshly revalidates authority and generations, burns accepted or rejected valid nonces, and remains the sole writer of settings, decisions, proposals, audits, responses, exports, and skills. Unknown fields/actions, stale versions, cross-project requests, missing elevated confirmation, and replay fail closed.

The runtime report relays only the official current `TuiPluginApi.app.version` from this package's separately loaded TUI module. It binds the project, canonical-root identity, same-account live publisher PID, issue/expiry times, and one random generation nonce; publication is `0600`, expiry cannot exceed 60 seconds, refresh occurs every 15 seconds, and disposal removes only a matching generation. Consumption requires the selected state root, bridge ancestors, and final file to be owned by the server's effective UID, requires the report file to remain exactly `0600`, and rejects a state root or bridge ancestor that is group/other writable. `EPERM` does not prove same-account publisher liveness. Dead, inaccessible, expired, malformed, cross-owner, permissive, cross-project, and cross-root reports are rejected and cleanup removes them. A host that cannot establish effective-UID ownership cannot use this relay. The report is operational IPC, not a decision/control envelope and not exported.

The OpenCode state root is the canonical mailbox boundary. Every existing component from that boundary through `self-evolve`, `bridge`, project, namespace, and final file is checked with `lstat` and `realpath` containment. Symlink ancestors/finals, special files, and material hard-link aliases are rejected. Final reads and creates use `O_NOFOLLOW` where supported, restrictive modes, same-directory operations, and create-exclusive publication; unsupported no-follow operation fails closed. Paths are revalidated immediately before and after reads/publication/unlink as far as Node's standard filesystem API permits. The host-version report applies the additional effective-UID, ancestor-write, exact-mode, and same-account PID checks above. Cleanup and dead-lock recovery use the same path rules and never follow request/response symlinks.

After the factory returns, the server derives host authority through bounded version resolution from official `PluginInput` surfaces. Redirects, alternate origins, user-configured URLs, authentication failures, malformed replies, and unsupported versions fail closed. Host-global skill discovery separately composes exact-origin `/path`, global and project `/config`, and global and project `/skill` projections; the stable aggregate skill list alone never proves global provenance. Only canonical local entries whose host projections agree can become existing targets. Built-in, URL/embedded/cache, project-only, ambiguous, malformed, or drifted entries remain read-only/ineligible.

State-root precedence is explicit validated option, synchronous official host state, bounded official path SDK, then standard environment reconstruction only when no official API exists. On OpenCode 1.18.3 a compatible server may use an environment root provisionally for a read-only persisted-mode lookup while startup would self-block the SDK. It cannot open the store, mutate settings, process autonomous events, or gain skill authority until post-start SDK validation matches. Timeout, unavailability, or mismatch leaves the runtime suspended, exposes a bounded reason, and requires explicit root configuration and restart; no automatic root migration or merge is permitted.

Project evidence and global contributions are joined only by a project-local intent/link containing a random UUID-v4 allocation. Global contribution files are immutable, exact-schema, and contain no project/scope identity, path, prose, excerpt, command, session, observation, capsule, cluster, evidence-domain, or local-incident value. Purge-all publishes an accepted-terminal response, stops authority and timers, and then removes the entire self-evolve state subtree after a bounded handoff. Project-scoped contribution purge and support recomputation remain part of the global lifecycle slice. Revoking aggregation consent stops new contributions immediately but does not silently erase committed retained data.

Long-lived privacy guards re-read durable permissions and automation generation for every excerpt and contribution publication, and the store checks them again under the mutation lock before allocation. Revocation by the same process or another process atomically turns automation Off, advances the generation, and blocks new artifacts.

`export all` is a sensitive, user-requested archive. It includes global settings and identity-free global lifecycle state plus only the acting project's private partition, record/index data, separately classified and bounded bridge metadata, active proposal-content chunks, and rollback snapshot bodies classified as `sensitive-skill-snapshot`. `global-recommendations` excludes project evidence, global settings, contributions, and aggregates. Active content can reveal skill instructions; terminal/purged content is excluded. Descriptor-bound reads reject symlinks, hard links, replacements, unknown bridge fields, and path/project binding mismatches. Native export streams JSON into an exclusive `0600` artifact below a private `0700` export directory, permits one active job, caps one artifact at 64 MiB and temporary export storage at 128 MiB, publishes SHA-256/size/path/expiry metadata, and never auto-opens it. Exports exclude other project partitions, lock/temp files, the TUI host-version runtime report, raw quarantine corruption, unrelated OpenCode state, complete transcripts, raw messages, and raw host session/message IDs.

## Local Account Trust Boundary

The state root and both plugin targets run with the user's OS account. The filesystem protocol prevents accidental cross-project/root use, stale generations, link/path attacks, and malformed or replayed package messages; it is not cryptographic isolation from arbitrary code already running as that same account. Such code can edit OpenCode configuration and durable state and may already write user-owned skill files directly. Do not load untrusted server or TUI plugins. Protecting against a malicious same-account process is outside this plugin's enforceable boundary.

The project storage quota is total across repository settings, record files, indexes, snapshots, leases, quarantine artifacts, and project bridge files. Project-size calculation, projected store writes, and decision/control/operation request publication run under the same cross-process mutation lock and reject symlinks. Request publishers additionally share a 64-file cap, a mailbox budget of the smaller of 512 KiB or one eighth of project quota, response reservation, and a store-capacity reserve. Native export uses its separate fixed temporary quota so it cannot silently consume the durable project budget. A mandatory settings/audit event may exceed an already exhausted cap only when the appended audit envelope is at most 4 KiB; this narrow exception preserves a safety-relevant control-plane outcome and is not available to recursive failure logging or ordinary records.

Purge-all is terminal for the current store/integration instance. Timers, scheduler work, and mailbox polling stop before command return; subsequent events and commands require restart, and disposal does not recreate the subtree.

## Permanent Prohibitions

No preference, permission, or allowlist can permit:

1. Spawning implementation, shell, or Git agents.
2. Git commits, pushes, publication, or external-tracker mutation.
3. `client.session.promptAsync` or `client.tui.appendPrompt`.
4. Synthetic messages in the working-session transcript.
5. Invoking the working agent's question tool from the server plugin.
6. Persisting complete transcripts or raw message bodies.
7. Applier access outside a current host-global existing target or exact explicit creation root.
8. Model-authored source, scope, retention, budget, permission, preference, or apply decisions.
9. Silently rewriting Automatic recommendations when an operational suppressor fires.
10. Stale-generation automatic work or Off-window/pre-Off backfill after re-enable.

## Emergency Stop

Set `SELF_EVOLVE_KILL=1` before startup for a process-local fail-closed downgrade, use the native Control Center safety controls, or run `/self-evolve kill-switch on` in a headless environment. Emergency Stop suppresses automatic work and new Apply without silently changing Automatic recommendations, and the downgrade is audited. Exact risk-reducing Undo remains independently gated.
