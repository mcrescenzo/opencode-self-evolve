# Security Policy

## Reporting

Report security issues privately through GitHub Security Advisories for `mcrescenzo/opencode-self-evolve`. Do not open a public issue for an undisclosed vulnerability. Never include live secrets; use synthetic values that preserve the relevant token shape.

Relevant reports include privacy-boundary bypasses, analyzer isolation failures, unsafe path handling, stale-hash or symlink bypasses, unauthorized application, audit/rollback defects, synthetic transcript injection, and unexpected external mutation.

## Privacy Classes

- Complete transcripts and raw message bodies are never stored.
- Deterministic receipts and typed observations are stored without raw text.
- Sanitized evidence excerpts require separate explicit consent, are length-bounded, and have a short lifetime.
- Skill hashes are durable. Proposal bodies are bounded typed chunks tied to one proposal ID and proposed-content hash. Readers reject cross-proposal, mixed, duplicate, partial, non-canonical, or hash-mismatched sets. Bodies exist only while required by an active proposal and are replaced by hashes when it closes.
- Cross-project aggregation is disabled by default and requires both sanitized-excerpt and cross-repository consent. Global claims use an exact normalized schema and contain no paths, project/repository/customer identifiers, commands, or text; provenance is a non-reversible incident hash.
- Observations and observation-like evidence default to 30-day retention; proposals, decisions, audits, rollback/intervention/circuit records, and snapshots to 90 days; and decision/control/operation bridge envelopes to a fixed 24 hours. The operational TUI host-version report expires within 60 seconds, is revoked on clean TUI disposal, and is omitted from exports. Native export artifacts have a separate short expiry and are deleted by project or all-state purge. Aggregate claims receive a 30-day default explicit expiry when created. Active critic-pending/pending/approved/applied chains, required proposal content, and snapshots remain until terminal. Terminal transitions and proposal purge compact content immediately under the transaction lock; boot/read recovery finishes interrupted compaction before records are exposed or exported.

Redaction is defensive, not a secrecy guarantee. Users should not scan material that must never reach their configured model provider.

## Applier Boundary

The applier is the only code path authorized to write skill files. Every target must be contained by an explicit canonical absolute-root allowlist. Existing edits are bound to the exact approved current hash; a new target is bound to the exact `must-not-exist` sentinel. Symlinks anywhere in the path are rejected. Existing writes use a complete same-directory temporary file and atomic rename. New files are fully written and validated before an atomic create-exclusive hard link publishes the complete inode; the temp name is then unlinked. Readers therefore see absence or complete content, never an empty reservation. Filesystems that do not support this hard-link primitive fail closed without a rename fallback. Exact readback hashing, append-only audit, and rollback guarded by `currentHash == appliedHash` remain mandatory. Scope ambiguity, stale hashes, collisions, privacy or injection flags, lease conflicts, missing allowlists, secret canaries, growth limits, audit failure, and rollback uncertainty all fail closed.

Auto approval is per change. TUI and headless approval must bind the proposal ID, current target hash, proposed-content hash, exact decision version, and a server-issued one-use nonce. The server burns the nonce through a store-owned recoverable proposal-plus-decision transaction; a missing, mismatched, stale, or replayed tuple cannot authorize application. Interrupted intents recover under the mutation lock, while malformed/newer/conflicting intents are quarantined and fail boot closed. Apply recovery first claims the same deterministic process-aware lease as the writer. A live owner is a healthy deferred condition and causes no failure audit, rollback, snapshot deletion, or proposal transition; dead owners are reclaimed and recovered idempotently. An actual application or recovery failure transitions an approved proposal to a visible critical `failed-closed` record and revokes Apply authority. Manual remains advisory and never applies. Yolo remains bound to its explicit allowlist and release gates.

Every provider synthesis call requires both a process-aware project/cluster/target lease and a prior strict content-free `synthesis-attempt` admission. The lease spans admission, provider work, critic decision, content persistence, and terminal outcome. A pre-critic proposal is `critic-pending` and has no inbox, command, TUI, approval, or apply authority. Boot defers attempts owned by a live PID without writing an outcome or changing a proposal; dead owners are reclaimed before existing recovery resolves the residue. Recovery is idempotent, writes one outcome, does not repeat provider work, and does not let terminal failures suppress the cluster forever. PID reuse and `EPERM` liveness checks fail safe as live ownership.

## Cross-Process TUI Boundary

The TUI may write only create-exclusive authenticated envelopes in the separate decision, control, and operation request namespaces under `<stateRoot>/self-evolve/bridge/<projectFingerprint>/`, plus one replaceable short-lived `tui-host-health.json` runtime report. It reads strict server-authored projections and bounded inspection summaries but is read-only for global/repository settings and project records. Projections bind a SHA-256 identity of the selected canonical root; the TUI validates it before reads or submissions, so an explicit/projection mismatch fails closed. Control and operation requests bind the project, actor, timestamp, request ID, exact allowlisted action payload, target-derived generation/domain versions, and a server-issued one-use nonce. The server consumes every request namespace under one mailbox lease, freshly revalidates authority and generations, burns accepted or rejected valid nonces, and remains the sole writer of settings, decisions, proposals, audits, responses, exports, and skills. Unknown fields/actions, stale versions, cross-project requests, missing elevated confirmation, and replay fail closed.

The runtime report relays only the official current `TuiPluginApi.app.version` from this package's separately loaded TUI module. It binds the project, canonical-root identity, same-account live publisher PID, issue/expiry times, and one random generation nonce; publication is `0600`, expiry cannot exceed 60 seconds, refresh occurs every 15 seconds, and disposal removes only a matching generation. Consumption requires the selected state root, bridge ancestors, and final file to be owned by the server's effective UID, requires the report file to remain exactly `0600`, and rejects a state root or bridge ancestor that is group/other writable. `EPERM` does not prove same-account publisher liveness. Dead, inaccessible, expired, malformed, cross-owner, permissive, cross-project, and cross-root reports are rejected and cleanup removes them. A host that cannot establish effective-UID ownership cannot use this relay. The report is operational IPC, not a decision/control envelope and not exported.

The OpenCode state root is the canonical mailbox boundary. Every existing component from that boundary through `self-evolve`, `bridge`, project, namespace, and final file is checked with `lstat` and `realpath` containment. Symlink ancestors/finals, special files, and material hard-link aliases are rejected. Final reads and creates use `O_NOFOLLOW` where supported, restrictive modes, same-directory operations, and create-exclusive publication; unsupported no-follow operation fails closed. Paths are revalidated immediately before and after reads/publication/unlink as far as Node's standard filesystem API permits. The host-version report applies the additional effective-UID, ancestor-write, exact-mode, and same-account PID checks above. Cleanup and dead-lock recovery use the same path rules and never follow request/response symlinks.

After the factory returns, the server derives host authority through bounded version resolution. It prefers `client.global.health()` and permits exact-origin GET `/global/health` from official `PluginInput.serverUrl` only when the SDK method is missing or has a recognized transport/capability failure; redirects, alternate paths, query strings, fragments, user-configured URLs, non-HTTP protocols, and authentication/other authoritative SDK failures do not fall through. If both global-health paths are unavailable in an embedded TUI, the server may accept the live strict runtime report above, but it still validates the official state root before store creation or autonomous authority. Only healthy or current-TUI-reported stable OpenCode versions `>=1.18.3 <1.19.0` proceed; stable build metadata is allowed and prereleases are not. Unavailable, timed-out, authoritative-error, unhealthy, malformed, prerelease, older, and 1.19.x/2.x results fail autonomous authority closed; user-supplied version/support options cannot widen authority. After an unavailable startup, only the first later command gets one fresh recovery attempt. A persisted-auto/yolo provisional event hook has no integration before resolution and remains inert on failure. Status and health report pending or the observed version/`unknown` plus reason.

State-root precedence is explicit validated option, synchronous official host state, bounded official path SDK, then standard environment reconstruction only when no official API exists. On OpenCode 1.18.3 a compatible server may use an environment root provisionally for a read-only persisted-mode lookup while startup would self-block the SDK. It cannot open the store, mutate settings, process autonomous events, or gain skill authority until post-start SDK validation matches. Timeout, unavailability, or mismatch leaves the runtime suspended, exposes a bounded reason, and requires explicit root configuration and restart; no automatic root migration or merge is permitted.

Project purge removes that project's records, snapshots, mailbox files, native export artifacts, local aggregate index, and indexed aggregate contributions while preserving global settings. Purge-all publishes an accepted-terminal response, stops authority and timers, and then removes the entire self-evolve state subtree after a bounded handoff; boot recovery consumes an interrupted terminal intent. Revoking aggregation consent stops new contributions immediately but does not silently erase retained data.

Long-lived privacy guards re-read durable consent for every excerpt and aggregate contribution/read. Revocation by the same process or another process therefore blocks new excerpt/aggregate operations without replacing the guard.

`export all` is a sensitive, user-requested archive. It includes global settings and aggregates, every project partition, record/index data, separately classified and bounded decision/control/operation request/response metadata, classified control-state metadata, active proposal-content chunks, and bounded rollback snapshot bodies classified as `sensitive-skill-snapshot`. Active proposal and snapshot content can reveal skill instructions; terminal/purged proposal content is excluded. Descriptor-bound reads reject symlinks, hard links, replacements, unknown bridge fields, and path/project binding mismatches. Native export streams JSON into an exclusive `0600` artifact below a private `0700` export directory, permits one active job, caps one artifact at 64 MiB and temporary export storage at 128 MiB, publishes SHA-256/size/path/expiry metadata, and never auto-opens it. Exports exclude lock/temp files, the TUI host-version runtime report, raw quarantine corruption, unrelated OpenCode state, complete transcripts, raw messages, and raw host session/message IDs. Session lineage and advancing message cursors are domain-separated SHA-256 hashes; a bounded-window cursor gap advances without producing evidence from unknown overlap.

## Local Account Trust Boundary

The state root and both plugin targets run with the user's OS account. The filesystem protocol prevents accidental cross-project/root use, stale generations, link/path attacks, and malformed or replayed package messages; it is not cryptographic isolation from arbitrary code already running as that same account. Such code can edit OpenCode configuration and durable state and may already write user-owned skill files directly. Do not load untrusted server or TUI plugins. Protecting against a malicious same-account process is outside this plugin's enforceable boundary.

The project storage quota is total across repository settings, record files, indexes, snapshots, leases, quarantine artifacts, and project bridge files. Project-size calculation, projected store writes, and decision/control/operation request publication run under the same cross-process mutation lock and reject symlinks. Request publishers additionally share a 64-file cap, a mailbox budget of the smaller of 512 KiB or one eighth of project quota, response reservation, and a store-capacity reserve. Native export uses its separate fixed temporary quota so it cannot silently consume the durable project budget. A mandatory settings/audit event may exceed an already exhausted cap only when the appended audit envelope is at most 4 KiB; this narrow exception preserves a safety-relevant control-plane outcome and is not available to recursive failure logging or ordinary records.

Purge-all is terminal for the current store/integration instance. Timers, scheduler work, and mailbox polling stop before command return; subsequent events and commands require restart, and disposal does not recreate the subtree.

## Permanent Prohibitions

No mode, consent, or allowlist can permit:

1. Spawning implementation, shell, or Git agents.
2. Git commits, pushes, publication, or external-tracker mutation.
3. `client.session.promptAsync` or `client.tui.appendPrompt`.
4. Synthetic messages in the working-session transcript.
5. Invoking the working agent's question tool from the server plugin.
6. Persisting complete transcripts or raw message bodies.
7. Applier access outside the canonical allowlist.
8. Model-authored scope, retention, budget, consent, or apply decisions.
9. Silently rewriting the stored mode when a kill switch fires.

## Emergency Stop

Set `SELF_EVOLVE_KILL=1` before startup for a process-local fail-closed downgrade, use the native Control Center safety controls, or run `/self-evolve kill-switch on` in a headless environment. A kill switch prevents autonomous application without silently changing the user's stored mode preference, and the downgrade is audited.
