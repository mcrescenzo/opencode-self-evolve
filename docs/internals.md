# Internals

Version 0.2 is a dual-target Node ESM package built around one durable pipeline:

```text
observe -> persist -> correlate -> synthesize -> validate -> notify | apply
```

Manual, auto, and yolo modes share the same evidence thresholds. Mode changes authority and scheduling, not proposal quality.

This file describes the implemented v0.2 architecture. Native TUI API rendering is tested with mocks; the isolated live smoke proves target loading, durable server integration, and filesystem mailbox behavior without external provider calls. Its production command-route check uses a loopback mock provider because OpenCode 1.18.3 continues the configured model turn after `command.execute.before`.

## Dual Targets

- `self-evolve.js` is the headless-safe server entry at `.`. It default-exports only `SelfEvolvePlugin`, imports no TUI target or `@opentui/*` runtime, owns durable writes, and exposes commands/events.
- `self-evolve-tui.js` is the native review entry at `./tui`. Its default export has `{ id: "mcrescenzo.self-evolve", tui }` `TuiPluginModule` shape. It renders consent, proposal, audit, and rollback UI and relays official `api.app.version` for embedded hosts, but is not the durable observation/proposal/audit writer.
- Shared modules are pure server-side ESM helpers and import neither package target.

The package checker installs the packed tarball into a fresh consumer, imports both export paths, verifies the server without OpenTUI peers, checks the namespace shapes, enforces the exact public file manifest, and rejects network/process module imports.

## Autonomy Modules

1. `self-evolve-schemas.js` defines immutable records, settings, modes, budgets, decisions, transitions, and authority evaluation.
2. `self-evolve-store.js` owns versioned project-partitioned JSONL state, atomic records, leases, CAS, retention, and corruption handling.
3. `self-evolve-observation.js` extracts deterministic receipts, forms bounded structured observations, and correlates independent incidents.
4. `self-evolve-inventory.js` discovers skill targets, canonicalizes allowlists, hashes content, rejects symlinks/unsafe paths, and enforces growth/canary checks.
5. `self-evolve-privacy.js` enforces project partitions, consent, redaction, quotas, retention, export, and purge.
6. `self-evolve-synthesis.js` runs hidden deny-all-tools synthesizer and critic sessions with strict schemas and current-content hash binding.
7. `self-evolve-applier.js` is the sole skill writer: leased, hash-bound, allowlisted, atomic, audited, readback-verified, and rollback guarded.
8. `self-evolve-commands.js` parses and executes deterministic mode, consent, inbox, decision, export, purge, and kill-switch controls.
9. `self-evolve-pipeline.js` composes observe, correlate, synthesize, critic, notify, approval, application, and rollback stages.
10. `self-evolve-scheduler.js` debounces idle events, enforces durable leases/budgets/quiet periods, rejects stale epochs, and keeps event handling non-blocking.
11. `self-evolve-integration.js` resolves effective authority, coordinates scheduler/pipeline/TUI, boots recovery, and shuts resources down.
12. `self-evolve-state-root.js` implements canonical dual-target root precedence, bounded SDK resolution, and root identities.
13. `self-evolve-tui.js` presents native safe-idle dialogs and durable inbox/audit results.

## Hooks And Boot

The server always registers `config`, `command.execute.before`, and `dispose`. The config hook installs the hidden compatibility analyzer agent. Durable v0.2 is the default; only `durableAutonomy: false` selects the legacy path. The factory performs only a read-only persisted-mode lookup against a synchronous root candidate and returns hooks before host calls begin. One timer then runs a single startup state machine: bounded host-version resolution, root resolution/validation, integration creation, boot, and orphan recovery. Version resolution prefers `client.global.health()`. A missing method or recognized SDK transport/capability error uses exactly `/global/health` from the validated origin of official `ctx.serverUrl`; authentication and other authoritative SDK failures do not fall back, and an SDK timeout does not overlap the still-running call with another request. Transient transport errors and cancellable fallback timeouts retry with exponential backoff inside one fixed five-second window; invalid official inputs and authoritative health/version failures do not retry.

If both server-side global-health paths are unavailable in an embedded TUI, startup may read the package TUI target's `tui-host-health.json`. The TUI copies only official `api.app.version` into an exact-schema `0600` report bound to project, canonical root, same-account live publisher PID, random generation nonce, and a maximum 60-second lifetime; it refreshes every 15 seconds and conditionally revokes its own generation on disposal. The report, state-root boundary, and bridge ancestors must match the server's effective UID, the report must remain exactly `0600`, and neither the state root nor bridge ancestors may be group/other writable. `EPERM` or unavailable effective-UID validation fails this relay closed. The server checks the report only after global health is unavailable and still requires official root validation before store boot. Stable build metadata is accepted; prerelease, unsafe numeric, malformed, older, and 2.x versions fail closed. After exhausted startup, only the first later `/self-evolve` command serializes one fresh bounded version, root-validation, integration, and boot run. Concurrent commands share that attempt, failure remains authority-free and latched, and success atomically installs the recovered runtime before dispatching the initiating command. A module-level in-memory coordinator keyed by official host identity, project/root identity, and authority-narrowing options shares initial and late runtimes across duplicate factory hooks, deduplicates the same command/event input object, and closes the integration only after the last matching factory disposes. Different host origins, client identities, or narrowing options never share. Recovery cancellation is coordinator-owned: disposing one factory leaves shared work alive for remaining users, while final disposal interrupts and settles it. Failed health text includes only bounded categories, never raw SDK/fetch error messages. The resolved version is passed unchanged into boot, and user options cannot widen it.

Root precedence is explicit option, synchronous official host field, official path SDK, then environment only when official APIs are absent. Because OpenCode 1.18.3 exposes no documented synchronous server state field and `client.path.get()` can self-block project initialization, a standard XDG/HOME root is provisional after compatibility succeeds: startup may read current settings from it without creating or rewriting anything solely to preserve persisted manual/auto/yolo hook selection. A timer scheduled before return performs the bounded path call only after the factory returns. Exact match opens the store and runs boot recovery before any event or command gains authority; timeout, unavailable API, or mismatch resolves the runtime closed and reports a restart-required health reason. No root is copied, merged, or migrated. The same post-start phase then retries host-session listing with bounded backoff, aborts only active self-evolve hidden sessions, caches health, and is cancelled and awaited by disposal.

The scheduler and pipeline keep raw host session IDs only in ephemeral call state. Durable cursors and scheduler audits use a domain-separated SHA-256 session-lineage hash. A cursor stores the hash of the last observed host message ID, or a deterministic hash of the bounded legacy message shape when no ID exists. The pipeline locates the prior cursor with `lastIndexOf` and observes only the unseen suffix. A prior cursor missing from the current 120-message window is an audited gap: the cursor advances, but the unknown overlap produces no receipt, observation, or synthesis.

A passive `event` hook is absent for persisted manual. Persisted auto/yolo may expose a provisional hook before health because OpenCode hook shape is fixed when the factory returns, but the handler reads only a settled runtime reference and returns immediately while validation is pending or failed. It cannot reach an integration, scheduler, provider, or applier before boot. Commands likewise report `startup-validation-pending`. Validated auto/yolo idle events reach the scheduler only after boot succeeds.

`dispose` clears the module-level legacy registry and asynchronously shuts down the integration, scheduler, applier, synthesis timers, audit buffers, and store.

## Hidden Analysis

The synthesizer and critic use hidden primary sessions, temperature 0, one step, strict structured output, and deny-all tool permissions. The observer is deterministic and makes no model call. Inputs are typed evidence, inventory, bounded optional excerpts, and current skill content; model output cannot select scope, consent, retention, budgets, or apply authority. Every child session is aborted after success, failure, or timeout, and boot recovers active orphans after a hard crash.

Passive auto/yolo work does not charge a provider call when the scheduler starts a cycle. Only an eligible synthesis operation requests slots. Immediately before starting the synthesizer, the pipeline asks the scheduler to reserve two slots for the synthesizer/critic pair. The scheduler serializes the fresh-settings check, rolling-hour durable count, and reservation writes with a project-scoped process-aware lease, then verifies one durable `scheduler-budget` / `passive` audit per requested slot before releasing the lease. Fewer than two remaining slots, lease contention, settings/read/write uncertainty, or failed readback defers closed before either hidden session starts. The pair is conservatively charged even if synthesis later no-ops or fails before critic. Manual command scans never receive this reservation capability and do not consume the passive budget. `synthesisPerDay`, quiet hours, episode leases, failure backoff, and the circuit breaker remain separate scheduler controls.

After deterministic preflight, synthesis acquires a deterministic project/cluster/target process lease before persisting one strict `synthesis-attempt` admission with a random domain-separated outcome ID, deterministic proposal ID, project/cluster/target binding, admission time, and state `admitted`. No prompt or content is stored, and failure to acquire or persist prevents the provider call. The lease remains owned through provider output, `critic-pending`, critic transition, typed content persistence, and the terminal `synthesis-outcome` audit. Boot defers a live owner without writing an outcome or changing the proposal; a dead owner is reclaimed before the prior recovery rules run. Replaying boot is idempotent and never calls the provider. Terminal cluster records no longer suppress later synthesis; ordinary failure backoff still applies.

## Decision CAS And Mailbox

TUI and headless decisions carry:

```text
(proposalID, targetHash, proposedContentHash, decisionVersion,
 actor, timestamp, nonce, priorState, newState)
```

The store applies compare-and-swap against `priorState` as one recoverable transaction. Under the existing mutation lock it persists `decision-transaction.json`, binding the project, prior proposal envelope ID, exact next proposal and decision envelopes, and whether terminal proposal-content compaction is required. It appends both sides idempotently, compacts terminal content, then removes the intent. Boot and ordinary reads recover every partial position without duplicate records or terminal content exposure. Malformed, newer, or conflicting intents are quarantined and fail closed. A successful transition increments the decision version and burns the nonce. Stale state, target/content hash mismatch, duplicate nonce, cross-project scope, or invalid transition fails closed. Auto requires an exact per-change approval, including in headless operation. Yolo may synthesize an internal approval only after allowlist and release gates pass. Rollback is valid only while the current disk hash equals the recorded plugin-applied hash.

The separate TUI process is read-only for settings and project records. It writes create-exclusive `0600` envelopes only to separate decision and control request namespaces, plus the replaceable short-lived host-version runtime report described above. Decision envelopes retain the proposal/hash/version/state tuple. Control envelopes use exact action schemas for mode, consent, repository exclusion, and allowlist replacement and bind a strict server-authored settings projection, canonical state-root identity, global `updatedAt`, full settings hash, actor, timestamp, request ID, project, and one-use nonce. The TUI validates the projected root identity before inbox/control reads. The server consumes requests under the mailbox lease, re-reads settings, calls the store's locked updater APIs, burns the nonce, and publishes bounded responses plus an optional refresh hint. The native keymap command `self-evolve.settings` renders `DialogSelect`, `DialogConfirm`, and `DialogPrompt`; it never writes settings directly. No undocumented `api.client.selfEvolve`, arbitrary command string, direct record append, or session prompt injection is part of the contract. Headless commands invoke server integration directly rather than writing mailbox files.

Mailbox paths share one canonical state-root boundary. Each existing component through the project and namespace is `lstat`/`realpath` checked for containment immediately around operations; final reads use `O_NOFOLLOW` and inode/link-count checks. Request/response publication is restrictive, same-directory, and create-exclusive. Symlink ancestors/finals, hard-link aliases, path replacement detected around open/publication, and unsupported no-follow platforms fail closed. Consumer-lock recovery and retention cleanup use the same path policy and unlink only validated in-bound entries.

## Durable State

Global settings use `<state-root>/self-evolve/global/settings.json`; each checkout/worktree uses `<state-root>/self-evolve/<projectFingerprint>/` for repository settings and records. Server and TUI call the same state-root and project-identity resolvers. Explicit roots must be canonical absolute paths. Official SDK results outrank and must validate a provisional environment root even when they disagree. Explicit project fingerprints are format-checked and must agree with derivable inputs. The fingerprint hashes a versioned tuple containing the canonical remote (or canonical repository root) and canonical absolute worktree path, so clones/worktrees isolate and relocation creates a new partition. Settings are read fresh before every command, cycle, decision, apply authorization, excerpt operation, and aggregate contribution/read. Store `updateSettings`, `updateGlobalSettings`, and `updateRepoSettings` callbacks perform their read, validation, field mutation, projected quota check, settings publication, and bounded audit in one cross-process lock critical section; callers never submit a full object built from an unlocked read.

Records are append-only JSONL except lifecycle compaction. Proposal bodies use strict `proposal-content` records co-located in `proposals.jsonl`; each chunk binds proposal ID, proposed hash, base64 encoding, index, and count. Readers require one complete canonical set and verify the decoded SHA-256. Active critic-pending/pending/approved/applied content survives retention; rejected/failed/superseded/rolled-back and purged proposal content is deleted immediately. Valid legacy content audits migrate to typed chunks and all legacy body audits are removed. Cross-project global-skill claims are separately consented, strict normalized records in `global/aggregates.jsonl`, with local project contribution indexes for purge. Store writes use same-directory temporary files and rename, while leases use create-exclusive files. Existing skill replacement uses rename. New-skill publication validates the full same-directory temp and uses an atomic create-exclusive hard link followed by temp unlink; unsupported filesystems fail closed rather than using an overwrite-capable fallback. Recovery recognizes a complete published hash or removes only a same-directory, name-bound, hash-proven plugin temp. Complete transcripts, raw message bodies, and raw host session/message IDs are never stored. Observations keep incident identity separate from their exact SHA-256 session-lineage hash; eligibility counts a lineage once across multiple incidents, and missing legacy lineage collapses to one unknown lineage. Retention defaults are 30 days for observations and observation-like evidence; 90 days for proposals, decisions, audits, rollback/intervention/circuit records, and snapshots; a fixed 24 hours for decision/control bridge envelopes; at most 60 seconds for the operational TUI report; and an explicit 30-day expiry assigned to aggregate claims. Startup recovery and daily sweeps enforce retention.

Quota accounting recursively sums every regular file in the project partition and project bridge directory, rejects symlinks/special files, substitutes pending replacement sizes, and compares once against `storageQuotaMiB` under the shared mutation lock. Decision/control request publishers use that same lock, a shared 64-pending-request ceiling, a `min(512 KiB, project quota / 8)` mailbox sub-budget, maximum-response and absent-control-state reservation, and a store-capacity reserve. Snapshot creation goes through the store for the same reason. A safety-mandatory settings audit append is capped at 4 KiB and is the only over-quota exception.

Project export remains scoped. State-root `export all` returns global settings/aggregates, all project settings/records/indexes, per-class bounded and classified decision/control request/response metadata, classified control-state metadata, and Base64 rollback snapshots labeled sensitive, while excluding raw quarantine and operational files such as `tui-host-health.json`. Purge-all marks the store and integration terminal before returning; no settings read, retention, mailbox, event, later command, or disposal path can recreate the subtree before restart.

Yolo rollout metrics scan only strict `synthesis-outcome` audits in this store, validate their producer and full bounded shape, enforce current-project binding, and deduplicate by outcome ID. Accepted and valid no-change outcomes are successes; critic rejection and failure are failures. Retained history must meet both configured thresholds. Injected counters and older synthesis/critic/pipeline diagnostic audits have no authority.

## Validation

Run `npm test`, `npm run check`, and `npm run pack:check`. `npm run smoke:live` is an optional no-external-token local host smoke: its fresh direct-registration child executes `/self-evolve health` through the production session-command route with a loopback mock provider, then proves process and temporary-state cleanup. Restart OpenCode after plugin, TUI registration, mode, or skill changes; existing sessions retain loaded plugin and skill content.
